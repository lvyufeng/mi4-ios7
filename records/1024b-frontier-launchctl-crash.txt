WHAT THIS MEANS, BY VALUE

1. THE 1023/1024 FRONTIER (pid 1's pthread-create data-abort loop) IS NOT THE WALL.  In THIS
   capture pid 1 got cleanly through: `launchd[1] has started up`, and the OS went on to start
   pid 2 (launchctl).  Whether or not 1024's VM_MAX_ADDRESS patch is what moved it, the boot is
   demonstrably past it here.  (This capture is NOT the 1024 arm -- it has no VM_MAX_SPLIT key --
   but it carries `xnu_live_abt_wdsplit=0x40000000` AND the SUBMAPSKIP start=0x40000000 rows, so
   the split-consistency is already in whatever arm produced it.)

2. THE NEW WALL IS A USERSPACE STACK FAULT IN launchctl (pid 2).  Geometry from the same capture:
       IOS7LAB shared region 0x2c000000..0x40000000; stack below 0x2be00000
   The fault VA 0x2bdbe000 is EXACTLY 0x2be00000 - 0x20000 (128 KiB) -- the top of the fixed
   stack window the tree's ios7lab_user_stack() supplies (osfmk/arm/status.c, 0x2BE00000; see
   build_entry.sh:31861-31905's G1 stack clause).  sp=0x2bdbd074 sits 0x7438 below the fault.
   r4=r6=0x2bdbe000: the faulting instruction touches the stack page itself.  Translation fault
   = the page is UNMAPPED.  So launchctl grew its stack down onto a page the kernel never
   backed -- the stack allocation is too small (or the guard is one page too high) for what
   launchctl needs.

3. IT IS NOT A CODE FAULT.  pc/lr are in the dyld shared cache (executable, mapped), and the
   abort VA/far are on the stack (data).  The shared-cache pc simply names where the faulting
   *instruction* lives; the *address* that faulted is data at 0x2bdbe000.

CHRONOLOGY PROOF THAT THIS IS THE 1024 PRESS'S OWN BOOT
  * 08:30 and 09:40 captures (recovered BEFORE the 1024 press): carry the MI4IOS6 entry banner
    and `bsd_init: done`, but ZERO `launchd ... has started up` and ZERO launchctl crash.
  * the 10:20-12:20 family (recovered AFTER the 1024 press at 09:41 + the operator's power
    press at 10:17): `launchd[1] has started up` AND `launchctl[2] ... System bootstrapper has
    crashed`.
  * host dmesg: 09:45:41 `18d1:d00d` (the bootloader->payload handoff) then dark; 10:17:25
    `2717:0368` -> 10:18:09 `18d1:4ee7` = the operator powering the phone back on; adb uptime
    confirms Android booted 10:17.
  So the ONE boot that got past bsd_init into launchd/launchctl is the boot that ran at ~09:41->
    dark, i.e. THE 1024 PRESS.  Its XNU wrote a ram console, the crash preserved it, and the
    recovery loop read it (13 byte-identical files) -- but the records read those as "the stale
    ROM" and never looked at what the boot actually reached.

  **CONSEQUENCE: the 1024 VM_MAX_ADDRESS fix WORKED.**  Before it (08:30/09:40) the boot stopped
  at/around the pid-1 pthread storm (bsd_init done, no launchd).  After it (the 09:41 press) pid 1
  cleanly reached `launchd[1] has started up` and the OS spawned pid 2.  The frontier MOVED, one
  layer out, to launchctl.

WHY THE SERIES DID NOT SEE THIS
  The 1024 press (09:41) was NON-RETURNING and its USB console never enumerated, so no capture
  exists of IT (records/1024-press-read.txt is correct about that).  But the FLASHED ROM's own
  ram-console slot still held a PREVIOUS resident run that DID get this far, and every recovery
  since (10:20-12:20) read that same slot -- 13 byte-identical files.  The slot was not
  overwritten because nothing booted the flashed ROM again; the phone has been up in Android
  (adb 4a2fe00b, uptime 2:06 at 12:20) since the recovery cadence started.
