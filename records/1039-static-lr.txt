BYTES  the file's only truncations of a branch live at 37c1e9a4 (4429 = `add r9,r5,#8`), 37c1e9aa

       truncation of the BL PAIR is 37c1e9a5 (4429 -> 4428|1).  So: the per-halfword encoder wrote

       branch targets (37c1e9a6/A, 37c1e9a9/E, 37c1e9b4/8) -- it is `tgt-8` of a BL, or `tgt-4`/`tgt+1`
       of a BLX.  No 4-byte disassembly can make it a return address; it is an ALL-ARM trap path, so
       no hardware Thumb-exchange ran between the BL and the abort.
INFER THE PRODUCER IS THE RELOCATOR, NOT DYLD.  The zero-slide image has even code pointers (Thumb BL
      targets are even in memory: 37c1e9a6, 37c1e9a8, 37c1e9ae, 37c1e9b8, 37c26470, 37c26474, 37c26476,
      37c2647a, 37c26480).  An even base plus an even slide (0x86c000) gives an EVEN lr.  An external
      binder (dyld's `lazy_*` helpers) does not write register state.  A RELOCATOR that adds slide to
      every relocatable 32-bit word and sets bit0 on the target (or just does `w |= 1`) writes 37c1e9af
      somewhere in the image, and an ARM linker puts BL-pair halves in LITERAL POOLS.  So the mechanism
      class is: "a literal-pool word in a slid image holds an ODD bit location; a load through slid
      [pc,#N] landed the aborting `ldrb r1,[r1,#0x10]` on it" -- i.e. the 1032 class "the abort is not
      at the pc the rows show".  NOT PROVEN here: WHICH table / which relocator line (OPEN).
BYTES  a42e-a38 (pc's page) and a1a6-a20 (lr's page) have NO `rst`, `add ip,ip,#12` and no literal
       pointer to a per-halfword byte table (f8df xxxx with xxxx landing on data).  So the per-halfword
       emitter is NOT IN THESE 0x600 BYTES; its site is OPEN.

BYTES  pc 37C26474 = `00 29` (`cmp r9,#0`); pc-2 = `097c` (`ldrb r1,[r7,#5]`, r7 is the pushed frame
       pointer) -- instances of the SAME odd halfword in the SAME page (pc 37c26472 odd, and 37c26476

       byte-tables read as code: (penalty, pc) = (0,0),(1,2),(2,1),(3,3) is the Thumb2 branch-decode
       nibble table; 0x7c is its most frequent byte (0x7c occurs at 37c1e972, 37c1e990, 37c1e9a0,
       37c26430, 37c264e8, 37c2656e -- each in the `idx<<2|tag` position).  Pattern: a thin
       decode-bridge over the relocator (xnu-fixups.c class / iOS 7's swift per-image fixup tables).
       Consistency row: pc and lr are in DIFFERENT libs under one slide, and both hold the same
       foreign bytes -- that only composes if one relocator ran over both.

2. HOW AN ODD lr COULD BE THE USER lr -- mechanisms, by file:line
====================================================================================================
INFER (i)   fleh_dataabt save: stmea sp,{r0-lr}^ (traps_lo.s:422) + str lr,[sp,#0x3C]
            (:425).  ABT bank = r0..r12; lr here is r14_abt = EXCEPTION-ENTRY lr, which is the
            FAULTING PC (minus 8 at :413), NOT the user's r14.  The save block is serial and uses only
            r0/r1/sp -- nothing can put an odd value into [0x38].  It does NOT write user lr anywhere.
INFER (ii)  return_to_user: ldmfd sp,{r0-lr}^ (cswitch.s:192) + movs pc,lr (:193).  spsr from
            [uss+0x40].  It restores oil (i) wrote.  A Thumb bank gives an ODD lr only after a real
            blx -- and the ERET that switched to Thumb (movs pc,lr, cpsr.T=1) requires an ODD lr, so
            an odd lr in a Thumb bank means the switch happened INSIDE ARM code (a corrupted pc/reloc
            word), not at a bank edge.
INFER (iii) machine_load_context (cswitch.s:106-133): r0=arg, `ldr r3,[r0,TH_PCB_ISS]` (:128),
            `mov r0,#0` (:129), `add r3,#16` (:129), `ldmia r3!,{r4-lr}` (:132), `bx lr` (:133).
            The ldmia auto-index writes the WALKED address (r3=iss+0x40) into TH_PCB_ISS, so the
            NEXT switch from the same block ldmias from iss+0x20 -> r4..r7 get {fault, spsr, pl, ...}
            and r0-r3 stay ZERO.  Blocks are per-thread kmem (vm_kernel_page_alloc, mach.c,
            thread_kernel_state); thrown away at thread exit -- the SAME class as a stale boot block.
            r0=0 from an EXCEPTION return is impossible: r0 always holds lr-8/4 on this path
            (traps_lo.s :425-:449), so a user r0=0 arrived some other way.
INFER (iv)  thread_exception_return (cswitch.s:144) loads uss[0x38] into lr -- the value from (i).
INFER (v)   lazy swizzle / thread_set_state with an odd lr: machine_thread_set_state (status.c:296)
            and act_thread_catt (status.c:509-521) write a thread's state from kernel data.  Neither
            produces an ODD lr from an EVEN (code, slide) pair on an all-ARM path -- only a writer
            that ORs 1 (or carries a pre-tagged word) does.  No such line was found in this tree
            (OPEN: the image-side binder is not in this tree).
INFER (vi)  the SHIM (mach_kernelrpc.c:66; build_entry.sh installs this tree's ios7 trap -15, NOT a stock row): entry `ldr r2,[sp,#44] / ldr r8,[sp,#40] / ldr r3,
            [sp,#36]` and tail `strs to [sp] / add sp,#0xc / pop {r4-r7,pc}` (docs/1022 §1).  Its
            saved lr is the user return word; a per-halfword fixup over TABLE B would tag it too.
INFER RANK 1: a relocator/fixup pass that writes odd bit locations into a DATA table (or over ARM
            code), and the aborting `ldrb r1,[r1,#0x10]` read one of its entries -- NOT a
            context-write path.  RANK 2: (iii) for r0=0 only.

1.5 r0 = 0 -- who enters user code with r0 = 0
====================================================================================================
INFER (a)   machine_load_context: r0=0 at :127, last write before bx (:131).  Its callers:
            startup.c:536-537 (boot thread, NOT launchctl) and thread.c/thread_act.c via
            machine_switch_context -> Switch_context (cswitch.s:70): when continuing an EXITING
            thread (continuation nonzero) it does NOT reload; on the loader side it reloads
            {r4-lr} from TH_PCB_ISS -- which is the kernel lr (pcb.c:337 iss->lr = thread_continue),
            so a user pc can NOT come from a loaded ISS.  A loaded r0=0 is therefore a
            CONTINUATION entry, not an exception return to the user.
INFER (b)   the shim returns rv (0 = KERN_SUCCESS) in r0 (mach_kernelrpc.c:... `return rv`), and
            swi_exit64 (:215) preserves r0/r1 across the tail -- a shim call that SUCCEEDED leaves
            r0=0 and the user continues with lr = the shim's return word.  THIS is a site that
            enters user code with r0=0 on the measured path (launchctl's vm_allocate/map64 calls
            return 0; 1038's vm_map64 rows result=0).  r1=0 is NOT explained by it (r1 is preserved).
