4. SHIFT CANDIDATES
====================================================================================================
  WITHDRAWN: the first version's "(a)+(b)+(c)+(d)" arithmetic.  It tested RLR = arm_ctx lr and
  RM = arm_ctx r10 against a SINGLE uss -- the capture (section 1.5) shows the faults are on a stack
  the uss does not describe, so a coherent shifted record does not exist to find.
  WHAT CAN STILL BE SAID:
    * A 4-byte misaligned shift is impossible on ARM.
    * Against the aborting stack's OWN word r1 = 0x399a16fb, a 32-bit load at [sp'+0x10] returning 0
      would require that word to be 0 -- it is not.  A 16-bit load would take 0x16fb & 0xFFFF = 0x16fb,
      also not 0.  Under that word the walk's loop CANNOT produce r1 = 0 by loading.  (This is also the
      1036 H-SHORTNAME reinforcement: the 32-bit-load model is dead; but see 1035 P1: device bytes
      at pc = 09 7c 00 29, which IS `ldrb` -- a byte load of 0xf9 is not 0 either.  OPEN: whose word
      is 0x399a16fb.)
    * The pc=0x399a1474 / [sp-4]=0x399a16fb adjacency (0x2A87) and r10 = 0x39aedc00 = 0x399a1474+0x3C78C
      are two .c-local addresses; they say the walk and its caller are adjacent functions, nothing about
      offsets.  But: 0x39aedc00 is in the shared-cache image; if a FILE VA == DEVICE VA there, the cache
      ran without relocation and the file VA of 0x399a16fb (and of the walk) can be searched.
    * "NOT in a 4-aligned slot of the sp-window": every in-window word is a 4-aligned value or a
      pointer ending in 0/4/8/C; a framed BL-to-Thumb return (bit0 set) can only be recorded as the
      ADDRESS of such a word (unions/bitfields), so no in-window slot can hold it.  1038 must read the
      two 2-bit-folded halfword maps of the in-window words (folds: bits 1-2, 9-10, 17-18, 25-26).
