THE ARITHMETIC THAT DECIDES IT
------------------------------
  far - ustack      = 0x2bd0e000 - 0x2bd0d000 = 0x1000   (one PAGE above the advertised stack top)
  ustack - sp       = 0x2bd0d000 - 0x2bd0c074 = 0x0F8C   (the block size - UNCHANGED from 1024-1027)
  far - sp          = 0x2bd0e000 - 0x2bd0c074 = 0x1F8C = 0x0F8C + 0x1000

Compare the SAME offsets on 1027 / 1026 / 1025 / 1024:
  far - sp == 0x0F8C  and  far == ustack  (the fault was AT the region top).

On 1028:
  far - sp == 0x1F8C  and  far == ustack + 0x1000  (the fault is ONE PAGE ABOVE the region top).

So the fix grew the region by exactly one page (mach_vm_allocate rounds `size + 16` to
`size + PAGE_SIZE`, docs/1028-design.md s.5) and THE FAULT MOVED WITH IT BY THE SAME PAGE.  The block
top and sp are unchanged (`ustack - sp` is still 0xF8C), so the failing write is NOT the block's top
word: it is a write at `p->user_stack + 0x1000`, one page ABOVE even the new region top.

WHAT THIS MEANS
---------------
* **H2 as a fix target is REFUTED.**  H2 said "the region ends flush with the block top, so the word at
  `far == user_stack` is unowned."  If that were the whole cause, growing the top by a page would have
  OWNED the word at `user_stack` and the fault would VANISH.  Instead it MOVED: userspace is writing a
  fixed distance ABOVE whatever the top is.  The boundary is not the block top.
* **The write target tracks `p->user_stack`, not the block.**  `far == ustack + 0x1000` exactly.  The
  consumer is deriving its store address from the advertised stack top (which `thread_userstack`
  returns to userspace, status.c:90/98) and writing one page above it - i.e. it treats the region as if
  it were `[.., ustack + 0x1000)` and writes at its top.  Raising `ustack` (the fix) raises the fault.
* This is the [[mi4-a-window-is-an-interval-not-a-function]] / "the boundary can be in a READER" shape:
  the failing party computes its address FROM the value we changed, so the value must be corrected at
  its SOURCE, not by growing an allocation the party does not consult.

NOT A NO-OP, NOT A BUILD DEFECT
-------------------------------
`xnu_live_ustack_rc = 0` (not the ANYWHERE fallback), the region's `final == req` and grew (the second
ustack row's exec has `req=0x2bdfd000`, whose top `+0x1000 = 0x2be00000` is exactly the "stack below
0x2be00000" boundary printed by the kernel).  The fix is present and effective - it simply moved the
fault instead of removing it.
