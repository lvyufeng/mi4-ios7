================================================================================================
The fix as written is a THIRD NO-OP of the 1028 class: base down a page AND extent up a page CANCEL,
so the region's exclusive top is UNCHANGED at `user_stack` — the SAME flush-top boundary. The design's
own §1 prose ("top = user_stack + PAGE_SIZE") contradicts its own code ("top = user_stack").

CHECK 1 — ARITHMETIC: **REFUTED.**
  Code (§1): `addr = trunc_page(user_stack - size) - PAGE_SIZE; mach_vm_allocate(map,&addr,size+PAGE_SIZE,FIXED)`
  `size` is mach_vm_round_page'd (+ optional +PAGE) => a PAGE multiple. `user_stack` is page-aligned on
  EVERY measured arm (0x2bd35000/0x2bdeb000/0x2bde0000/0x2bd0d000/0x2bd38000, all %0x1000==0).
    base   = (user_stack - size) - PAGE = user_stack - size - PAGE
    extent = round_page(size + PAGE)     = size + PAGE            (already page-aligned: NO growth)
    top    = base + extent = user_stack - size - PAGE + size + PAGE = **user_stack**
  COUNTER-VALUE (1029 geometry, ustack=0x2bd38000,size=0x00100000): base=0x2bc37000, extent=0x101000,
  top=0x2bd38000 == ustack. Claimed top user_stack+PAGE (0x2bd39000) is FALSE. The base-move and the
  extent-grow cancel exactly. (1028's top moved because it grew ONLY the extent; 1030 does NOT grow the
  top — it re-anchors the SAME top lower.) => CHECK 5 is therefore also answered: 1030 is NOT different.

CHECK 2 — THE GUARD PAGE: **HOLDS (shape), but the guard is now the NEW lower base, and the old base
  page becomes ordinary RW stack.** `prot_addr = addr` (moves down with the base);
  `prot_size = trunc_page(size - unix_stack_size(p))` uses the ORIGINAL `size` local (NOT size+PAGE),
  so prot_size is UNCHANGED (1028 measured 0x1000). Region moves from [old_base,ustack) to
  [old_base-PAGE, ustack); the page that WAS the guard (old_base) is now INSIDE the RW region — i.e.
  the guard just slides down one page with the base. LAB_USER_STACK/MAXSSIZ/VM_MAX_ADDRESS untouched.
  No guard/LAB break — but note the guard-slide is IRRELEVANT to the fault (see CHECK 4).

CHECK 3 — THE FALL-THROUGH: **HOLDS as a discriminator; the ANYWHERE branch re-creates flush-top.**
  On FIXED failure: `addr=0; mach_vm_allocate(...,size,ANYWHERE); user_stack = addr + size;` — this
  uses the ORIGINAL `size` (not size+PAGE) and re-sets p->user_stack to the new top. rc != 0 names the
  fallback (`xnu_live_ustack_rc`). Note also the FIXED-at-lower-base is MORE likely to collide here: it

  own §1.2 "the page below is occupied" NO-OP risk is REAL and now the allocate must also fit one page

CHECK 4 — THE WRITER / CRUX: **REFUTED — 1030 does NOT cover `far`.**
  By value (1029 rows, far=0x2bd39000 ustack=0x2bd38000 blk_hi=0x2bd38000 blk_lo=0x2bd37f44):

CHECK 5 — CROSS-CHECK vs 1028: **NOTHING IS DIFFERENT — the fault will FOLLOW (here, WILL NOT MOVE
