== THE READING (by value, from the recovered console) ==
The launchctl fault's discarded `vm_fault` return is now a NUMBER in the capture:

    xnu_live_abt_vmfkrv=1                 <- KERN_INVALID_ADDRESS
    xnu_live_abt_vmfkrv_far=0x2bd35000
    xnu_live_abt_vmfkrv_dfsr=0x00000807   <- translation fault, page (L2 descriptor invalid)
    xnu_live_abt_vmfkrv_prot=write
    xnu_live_abt_vmfkrv_pc=0x3b4ce756
    xnu_live_abt_vmfkrv_sp=0x2bd34074
    xnu_live_abt_vmfkrv_pid=2

  and the stack's shape, once per exec:

    xnu_live_ustack_req=0x2bd35000   size=0x00100000  fixed_addr=0x2bc35000  rc=0
    xnu_live_ustack_final=0x2bd35000 prot_addr=0x2bc35000 prot_size=0x00001000
    (pid 1 launchd: req=0x2bdcd000 fixed_addr=0x2bccd000 rc=0 guard=[0x2bccd000,+0x1000))

So: `mach_vm_allocate(VMF_FIXED)` SUCCEEDED (rc=0, no ANYWHERE fallback) and created the
entry [0x2bc35000, 0x2bd35000) = exactly 0x100000 = MAXSSIZ. The faulting VA 0x2bd35000 is
that entry's **EXCLUSIVE TOP** — one byte past the last byte — and it is a WRITE at
sp+0xF8C. `vm_fault` -> `vm_map_lookup_entry` returned FALSE, so `vm_map_lookup_locked`
returned KERN_INVALID_ADDRESS (vm_map.c:8761ff, verified by source), i.e. **no vm_map entry
covered the VA when the walk ran**.

RESIDENT, not a wedge: after the crash `xnu_live_wdt_pets` climbs 0x1 -> 0x3 -> ... -> 0x61
(lines 30390..32847) and the console prints
`com.apple.launchd 1 ... (com.apple.launchctl.System) The System bootstrapper has crashed:
Bus error: 10`. The kernel kept running; pid 2 died.

== THE SHARPER FACT (why this is not just "one byte past the end") ==
The earlier launchd crash (1024 arm) faults at far=0x2bdbe000 with sp=0x2bdbd074, where
0x2bdbe000 lies **INSIDE** launchd's own entry [0x2bccd000, 0x2bdcd000). Both crashes have

    far - sp == 0xF8C   (identical)

so the faulting instruction is `[sp + 0xF8C]` in both — and in launchd's case a VA that IS
covered by a live entry still failed the lookup. The ~0xF8C above the initial sp is the
initial thread's argv/env/stack-top area. So the class is "a VA that the map SHOULD cover is
not found by the walker" (the 1013c/1015 family), not a mere off-by-one at the region top.
Both stacks live in the SHARED REGION [0x2c000000, 0x40000000) whose routing is governed by
1024's STAGE90_XNU_VM_MAX_SPLIT switch (task map 4th arg 0x40000000 vs stock 0x80000000).

== 1026'S QUESTION ==
Name WHY an allocated entry's VA fails vm_map_lookup_entry, and fix it. Working hypotheses,
to be decided by value before building: (H1) the stack lands in a SUBMAP / shared-region
sub-map and the fault walks the parent map (map 0xc0005688 in the abort); (H2) the
VM_MAX_SPLIT change routes [0x2c000000,0x40000000) to a different vm_map than the one
`mach_vm_allocate` used; (H3) a hint/mask condition in vm_map_lookup_entry.
