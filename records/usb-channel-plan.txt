USB LIVE-KLOG CHANNEL - design + verification report   2026-10-20   (no device action, no build run)
==================================================================================================
Goal (operator): 「抓紧开始usb通道建立啊，否则你每次都得刷镜像」 - the kernel console streamed live over USB,
so an iteration is `fastboot boot` + watch, not press + cold recovery.

0. SHORT ANSWER
  Built (959-962): a full-speed 18d1:0910 device that streams the RAM-console ring out EP1-IN - but only
  from a poll hook on the IDLE loop, with no kernel thread, no interrupt, no debug-mode port, and it
  answered 4 of ~7 control requests a host's probe asks. The last recording that looked (press-1000,
  2026-10-13) has ALL FOUR rungs absent and no 18d1:0910 on the bus. The host reader attaches once and is
  typed into a person's shell. So: no live channel today. The plan below is NOT "fix the enum": enabling
  the stream on a crash that is not in idle is structurally impossible with an idle hook, and per-boot
  enumeration fragility is what makes a press cost a recovery. The client choice decides the design.

2. IF THE ENTRY IMAGE CARRIES ALL FOUR=1 - DOES THE HOST SEE IT?
  Conditionally, and it is not a property we control today.
  (a) In-IMAGE: yes, the site is right (check :40950-40963 pins D13 `__wrap_machine_idle`); the device
      arm will reset the link (`entry_usb_dev.c:346`) and the host must re-enumerate AFTER that - the
      reader's one-shot open is on the wrong side of that event if it attaches during the entry phase.
  (b) In-HOST: we need (i) a port left in DEVICE mode by aboot (the `USBMODE==2` gate; FORCE would drop
      an enumeration aboot already made - comment entry_usb_dev.h:130-136), (ii) the HOST's own probe
      to get through: GET_STATUS / SET_ADDRESS / GET_DESCRIPTOR x3 / GET_CONFIGURATION (stale buffer) -
      usually fine on Linux at FS, not a guarantee; (iii) the core to reach the IDLE path.
  (c) NOT while the kernel is executing: the poll runs only from `machine_idle`; during init/panic/hang
      nobody calls it. So "watching a live boot" works only in the quiet stretches - not a live console.
  Conclusion: STREAM=1 on the saved payload is necessary and NOT sufficient, and it costs every press
  one more unread variable. Do not make the USB channel a dependency of the current 1039 press.

3. WHAT IS MISSING (evaluated)
  (a) Enable in the payload build: the switches ARE entry-side; the saved record already has them. For
      a trial arm add `-DSTAGE90_XNU_USB_{PROBE,DEV,ENUM,STREAM}=1` to the script that writes the record
      (the main session's build_10NN.sh `$_arm_sw`) - I do not edit those scripts.
  (b) Kernel phase: the entry text is NOT inside XNU's executable (call 0 + 0x80001000, header
      entry_trace.c:20 / entry_stubs.c:35); static data (ring, stream buf) is inside XNU's rw image, so
      an XNU THREAD can read them. Nothing arms a timer IRQ today: `fleh_irq` (entry_stubs.c:3811) runs
      with XNU's page tables live, USB's 0x12500000 is not mapped there, and the idles' L1 hooks are
      compiled out (910a2 §9). NEEDED: a `NULL`-task-trampoline style spawn (entry side already used the
      technique for iokit stubs) + `ml_get_timebase`-programmed timer (DEADMAN gives the formula:
      0xf0000000 + 0x01000000*N) + a second L1 section for OTG + `entry_usb_*_irq()` that does the
      SETUP/complete work, then main == idle loops on a NAK state.
  (c) Host reader: add re-attach (open/claim/free in a loop: any bulk error, rc<0, or >=1 s of NAK ->
      free the handle and `libusb_open...` again; track re-enumerations and gaps in stdout/stderr),
      `--follow` for non-tty (append capture + echo), `--bell-on` patterns, and daemonize under
      `setsid` so it outlives a tool call. ALSO: spawning stdio from inside a live Python harness -
      `PYTHONUNBUFFERED=1`, never `--logout` on long-lived bridges, `cat > /dev/null 2>&1` for
      daemonized children (SIGPIPE-immune), PATH-qualified script paths (all learned in main today).
  (d) Cheaper than a press: no. Every iteration needs the new image on the phone, and the image goes on
      by `fastboot boot` (must stay, one-slot record untouched). BUT OS-SIDE iteration can be made
      press-free LATER: `gUSBDevice` (isochronous kdp-style console) is the kernel's own sink, so all of
      entry AND kernel output flow through ONE capture; a `KDP_READ`-style command could accept a
      segment write into a pre-mapped staging window. That needs an XNU thread + trap.c/DEFS work, i.e.
      AFTER frontier work, not now. ios-sweet (dipa-studio, SM7150) does the same shape over CDC-ECM
      UDP:5140 in USERSPACE after launchd - it does not help the crash loop we are in. No clone local
      (/mnt/data has none); not fetched (remote code is untrusted and unnecessary for this design).

4. THE DESIGN (client decision first)
  * If the working client is **libusb** (python) -> bare FULL-speed device, descriptor UNCHANGED
    (18d1:0910, 0xff/0x42/1) - Linux cannot early-suspend iface 0 of FS, so a "sleep-prone me" cannot
    stop the stream; speed is 12 Mbit but console volume is tiny.
  * If the working client is **macOS** (AppleUSBHostCompositeDevice) -> HIGH speed + IAD + CDC-ACM
    (class 2/2/1, the generic driver is loaded unconditionally).
  * Either way: interface 1 = SECOND BULK-IN DATA endpoint (ring only). EP1-IN keeps today's name-keyed
    text WITHOUT framing for old readers. Framing is on EP2 only: 16-byte header {magic 'MKLG'
    0x474c4b4d, seq LE32, head, epoch LE32, len LE16} so bytes lost in a host gap are DETECTED
    (`lost = head_b - prev_head_b`), never silently. `seq`/`epoch` disambiguate a cold boot vs reboot.
  * Device-side ring: 64 KiB, SPSC: producer = `entry_write_kv`-shaped writers (XNU printfs later),
    consumer = USB xfer; 2 buffers, xfer k outstanding, publish `head` only after clean+commit.
  * Settling: `usb_enum[.settle]` console var (0 CMD, 1 SETADDR, 2 CFG, 3 DATA-primed, 4 STREAM#),
    default 2 - fast-boot's "no device" is ambiguous.
  * Device can end a host's read early: `DIR_IN+TYPE_STD+RECIP_DEV+RNDIS` -> zero-length IN, then STALL
    as in Android's `allow_short` gadget (one-shot; V3 is press-free once the short-write bug is fixed).

5. ORDERED PLAN (lanes: mine = src/entry/entry_usb_*.{c,h}, tools/usb_*, tools/check_usb_*)
  P0 HOST-ONLY, today, no device:
     tools/usb_console_read.py: `--follow` (already appends; add reconnect + gap log + `--frames` that
       parses the 16-byte header if the rings are present), `--setsid` (re-exec in a new session),
       SIGPIPE-immune daemon mode, `--bell-on`, `--no-reset` (no libusb_reset_device, ever).
     Selftest: `--selftest-frames` (decode: clean run, dropped run, epoch change -> three distinct
       verdicts); `--selftest` on the fake backend (record a run into a pipe, kill it, prove re-attach).
     tools/check_usb_host_reader.py: extend to EP2 const + frame magic; mutate each; each must refuse.
     toolcheck: `python3 -m py_compile`, `tools/check_usb_host_reader.py --selftest`.
  P1 DEVICE-HOST-ONLY (compiles in a scratch dir - NOT out/stage90, NOT external/xnu... during a build):
     entry_usb_stream.{c,h}: (i) stop writing stream_* keys into the ring (moving counters to
       g_stage90_usb_stream_* statics); (ii) frame header on a SECOND buffer + a `--rings` compile flag
       OFF by default (old bytes byte-identical by extraction test); (iii) a completion count `n`;
       (iv) `entry_usb_stream_ring_publish(buf,len)` - the ONE writer interface, callable by any sink.
     entry_usb_enum.{c,h}: answer GET_CONFIGURATION from `g_usb_enum_configured`; accept SET_FEATURE/

6. RISKS
  * 1039 build in flight (pgrep build_10 shows PID 446779) - nothing here touches out/* or xnu.
  * Arm record carries STREAM=1 but no proof the stream ran: any report must say `no EP1-IN bytes`.
  * `STAGE90_HFS` MUST be 0 on D13 (memory); fastboot boot only; the one-slot last_kmsg record is NOT
    our channel and a fastboot boot of anything burns it.
  * The USB switch changes the D13 entry image every time - never an additional blind variable next to a
    rung whose device answer matters.
  * Client identity (libusb vs mac) changes interface layout; decide BEFORE P1 (the descriptor is a
    contract with check_usb_host_reader.py).
  * `entry_usb_dev_init` link-reset drops an enumeration aboot made - that is by design; the host must
    re-attach after it, which is why P0 comes first.
