3. THE FRAME ROWS CHANGE WITH EVERY RUN, AND THE LOG IS SHORT -- A RECTIFIER DROPPING THE TAIL
====================================================================================================
  EVERY near slot is IDENTICAL to 1035's (near0..near5 all equal; evf slot10 differs, 0x3a166ae0 vs
  0x388f7ae0), and xor_lr = 0x00711504, the same number.  near0..near4 are pc-relative words at ONE pc
  and they do not move between runs -- yet pc, lr, sp and r7 DO (all five differ from 1035's).  A fixed
  slide would move them together; a pc that moves while its neighbourhood does not means the ROW is not a
  reading of the pc the run executed, or the slide is fixed and pc's row is the earlier run's.  Either
  way, the pcc frame cannot be used as the trap frame.  Also evf_caller_r2 = 0xffffffff, r3 = 0x39b04020,
  r1 = 0, r4 = sp-4, and s0/s2/s4 (= r4 at sp-4, sp-4 again, sp) are the caller's stack, not the
  recovering function's.
  => The frame evf/pcc/pcc2 report is TRIMMED: it is not the trap frame.  It is a frame PUSHED BY
     the recovering function (copyin -> sleh_abort -> ... -> vm_fault) at or above the trap frame's sp.
     arm_ctx in this kernel is a POINTER PARAMETER; a nested frame's ctx copy and a stale/positional
     register read can each misplace a word.  THE MECHANISM IS NAMED AS A CANDIDATE, NOT PROVEN; what is
     proven is that the rows are not the trap frame's.
  THE LOG'S TAIL IS CUT AT A BOUNDED BUFFER -- the mechanism is NAMED, the edge is NOT measured:
  `debug_putc` (osfmk/kern/debug.c) writes while `(debug_buf_ptr-debug_buf) < (int)debug_buf_size` and
  SILENTLY DROPS every later character (BYTES of this tree's file); `debug_buf_size` defaults to
  `sizeof(debug_buf)` = DEBUG_BUF_SIZE and is RESET to it whenever the console is (re)initialised
  (debug.c:208), which this kernel does.  So a run's log CAN end at that edge, and anything printed after
  it is ABSENT, not "not reached".  THIS CAPTURE ENDS WITH "No errors detected", which is a natural end,
  not a pad -- so for THIS run the edge is not where the log stops; it does NOT follow that the rows are
  a complete account of the run (the frame anomaly above stands).
  Keep the hazard for 1037 all the same: a row printed after a large dump is unreadable by construction.
  => 1035 P1's "xor_lr != 0 => lr is not a file VA plus any slide" HAS A SECOND EXPLANATION: the xor
     compared the device's word with the file's word at the WRONG address.  Not a prompt to retract P1
     (pc and near0..near4 agreed under 0x50C000); a prompt not to build on the lr conclusion.
     AND -- after THIS run -- not to build on near0..near4 either without the pc in the same block (5).

6. THE CALLER IS A CANDIDATE, NOT NAMED: H-SHORTNAME  (HASH; supporting only)
====================================================================================================
  IF lr's file VA were 0x37C1E9AF (pc slide 0x50C000), lr would fall in libobjc's short-name hash
  (0x37C1E8F8..0x37C1E9B2; the only instance of its shape in the 316 MB cache, BYTES), on an ALIGNED
  16-byte block whose 4th word is [0x4FF0FF36, 0x3046, 0x5DF8048B, 0xBF00BDF0] -- i.e. the return
  address is the second halfword pair of that word (the "trimmed" shape 1035 saw at lr).  The hash's
  `mov.w r6,#0xffffffff` at 0x37C1E990 is a NAMED producer of -1, and 1035's frame has r2 = r5 = -1.
  H-SHORTNAME: the walk's r5 = -1 is the short-name hash's no-match return.  UNPROVEN -- it assumes
  lr's slide, which 5 leaves open.  1037 tests it: (i) the hash's own pc row on this thread, (ii) host:
  the two hash functions run over the 30-byte class names the cache's name section holds, (iii) the
  walk's load re-read as a 32-bit `ldr.w` -- r1 = 0 breaks the model.
