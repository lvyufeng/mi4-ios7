  CORRECTION 1 compared the alloca BASE against the OBSERVED r4 and concluded a down-alloca "cannot
  produce sp + 0x1F8C". That is a base-vs-cursor error: r4 is the post-increment CURSOR, so its INITIAL
  value (below sp) and its OBSERVED value (base + 4*k after k iterations) are different points in its
  life. The original static claim (`sub.w rN, sp, r#N, lsl #2`) is CONFIRMED VERBATIM.

  Arithmetic (the agent's, re-run by the lead):
    arm_ctx->sp at the fault   = 0x2bdac074
    writer push {..,lr} = 20   => sp at the `bl` = S_bl = 0x2bdac088
    r4_fault - S_bl            = 0x2bdae000 - 0x2bdac088 = 0x1F78
    model: r3_init = S_bl - 8*count ; r4_fault = r3_init + 4*k  =>  4k = 0x1F78 + 8*count
    => k integer and >= 0 for every count tested (count=0 -> k=0x7DE=2014, etc.). Consistent.
    r4_fault - sp      = 0x1F8C  (matches the 1030 frame)
    r4_fault - ustack  = 0x1000  (the region's exclusive top)

(4) OWED / NOT SETTLED — DO NOT OVER-CLAIM.
  The model REQUIRES, to be a complete account:
    (a) `count >= 2014` (an ~8 KiB VLA, == the value of the second alloca) — NEVER VERIFIED. The agent
        tested only that `k` is a non-negative integer.
    (b) `k <= count` (the cursor cannot advance past the loop bound) — the lead's re-run shows this is

  The honest state: **down-alloca CONFIRMED, cursor-overshoot PLAUSIBLE, the exact `count` and the

  ⚠ (b) IS NOT A HOLE TO FILL — IT IS A STANDING CONTRADICTION. `4k >= 0x1F78` (k >= 2014) is forced by

*** DECISIVE CONSEQUENCE ***
The caller does NOT compute the region's exclusive top. It builds r3 (the writer's r4) as the LOW end of a
`count`-word VLA buffer carved BELOW sp (block2_lo = sp0 - 8*count), and it is the WRITER's post-increment
cursor that walks UP. So the 1032 design's central premise - that 1031's cell will name a caller-side
computation of the TOP (CAL-CALLER-TOP) or of a base+size (CAL-CALLER-SIZE) - is NOT what the instructions
show: the caller's r3 is a plain below-sp VLA base, neither a top nor a base+size-of-the-region. The cell
1031 prints will compare r3 (=a VLA base near sp) against region_end; it should read r3 << region_end, i.e.
NEITHER CAL-CALLER-TOP NOR CAL-CALLER-SIZE, i.e. **CAL-CALLER-OTHER** unless the block2 buffer genuinely
reaches 0x2bdae000.
The open quantity is still `count` (r5, the return of 0x37c26698): it sets how far block2 reaches. If
count is large enough that block2_lo + 4*count (== block1_lo) reaches the region top, the OVERFLOW is in
this caller's own VLA sizing; if not, the writer's cursor runs PAST its own buffer. Either way the fix
belongs in THIS caller (its block sizing / count), NOT in any region geometry - consistent with s0.2.
