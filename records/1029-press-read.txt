CORRECTION (2026-10-17, lead; also records/1030-audit.txt) - WHAT ACTUALLY MOVES far
-------------------------------------------------------------------------------------
  ⚠ SECOND CORRECTION, 2026-10-17: an intermediate "far tracks sp, not the region extent" reading was
  itself WRONG and is retracted. The population of ALL 60 captures (recovered-unknown-arm-20261016-*,
  20261017-*) settles it by value:

    - `ustack - sp == 0xF8C` in **ALL 60** runs -- the argv/env block size is INVARIANT.
    - Pre-fix runs (1025/1026/1027 etc., 57 of them): `far - ustack == 0` and
      `far == base + size == e2_hi` -- far IS the SOURCE region's exclusive top.
    - Post-fix runs (1028 x2, 1029 x1, exactly 3): `far - ustack == 0x1000` and
      `far == base + size + 0x1000 == e2_hi` -- far IS the (H2-grown) region's exclusive top.

  So in EVERY run, **far == the region's EXCLUSIVE TOP**, and the ONLY thing that ever changed it is
  H2 growing the region (base+size -> base+size+0x1000). `far - sp` grew from 0xF8C to 0x1F8C purely
  because the TOP moved up while `sp` (and the block) stayed -- NOT because the writer reads `sp`. The
  earlier "far = sp + 0x1F8C is an sp-derived VLA base" was a mis-read of a correlation.

  => THE ORIGINAL 1029 CONCLUSION STANDS: far IS the region's exclusive end; the fault is a BOUNDARY
  WRITE at the region end; the writer (libobjc+0x14756 VLA cursor) writes AT the top of the owned
  region. This is why 1028 was a page-exact no-op and why 1030's base-move would ALSO be a no-op: any
  change to the region's top moves the writer's target with it, because the writer stores AT the top.
  The next rung cannot fix this by changing the region EXTENT. See records/1030-audit.txt.
  The 1029 probe DATA stands (all 10 keys, unchanged); the interpretation (boundary write) stands.

THE NEXT RUNG (1030) - what this reading licenses
-------------------------------------------------
  ⚠ The original "own the page at the region end" direction (make the region top land strictly above
  the block top) is a NO-OP: the writer stores AT the region top, so growing the region moves the
  writer with it (this is exactly why 1028's size+16 was page-exact no-op). The region-extent shapes
  below cannot work. The real requirement is to make the writer's target land INSIDE an owned page:
  either the writer must stop deriving its store from the (moving) top, or the region must extend far
  enough that the writer's NEXT store after the boundary is still owned -- but since the writer moves
  with the top, an extent change cannot do it. Instrument the writer's VLA-setup (libobjc+0x14756) to
  learn how the base is derived. Original (now-refuted) text:
  Make the region's exclusive top land STRICTLY ABOVE the block top by a whole page: anchor the base one
  page LOWER (addr = trunc_page(user_stack - size) - PAGE_SIZE) or size so top >= round_page(user_stack)
  + PAGE_SIZE. **Do NOT add to `size`** -- size + delta always rounds up to the old +0x1000 (1028 proved
  it). Own the page at the region END.
