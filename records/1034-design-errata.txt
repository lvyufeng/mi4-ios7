  / `6656 mov r8,fp` / `6658 str r5,[sp,#8]` ... is built from context, not from halfwords. The bytes

  pointer and regs[2] as a size -- both fit the shim.
  STATUS: the shim's push list must be re-decoded halfword-by-halfword before 2.2's list is quoted

E7. THE OUT-PARAM WIDTH DEFECT IS NOT IN docs/1034 — IT IS IN THE APAPTER, AND IT IS NOW THE PRIME
    HYPOTHESIS FOR "the caller never learns the address"
====================================================================================================
  MEASURED, extract offset = VA - 0x2C000000, both parities printed:
    0x381c6618  b5f0 af03  push {r4-r7,lr}; add r7,sp,#12
    0x381c6620  b08c 468a  sub sp,#0x30; mov sl,r0
    0x381c6652  4651 9a0b  mov r1,r10 ; ldr r2,[sp,#44]
    0x381c6658  9502 461c  str r5,[sp,#8] ; mov r4,r3
    0x381c665c  f8cd a028  str.w r10,[sp,#40]      <-- the word at r7+8 = SL = the ADDRESS POINTER,
    0x381c6666  4665 46f2  mov r5,r12 ; mov r10,?  (the second argument setup; both consts)
    0x381c6668  46f2 f7ff e97a  bl 0x381c5960 (the -15 stub, via the BL encoding at 0x6668)
    0x381c66b4  f001 fc5e  bl 0x381c7f74 (the MIG demux; the sentinel leg)
  So [r7+8] = the address pointer AND the adapter's out-param (regs[1] = that pointer) is the same
  word. The adapter writes the out address as a u64 (mach_kernelrpc.c:283-286 `copyout(&address64,
  regs[1], sizeof(address64))` = 8 bytes). The shim's own post-call read at 0x381c66ba onward
  (`0x381c66c8 ldr.w r0,[sl]`, `0x381c66c0 str r?,[sp,#?]`, verified halfwords 0x66c8 = f8d6 c000)
  reads a 4-byte address. A u64 copyout stores {addr32, 0} = a 4-byte address only if the adapter
  writes the HIGH word 0. It does (`address64 = (uint64_t)address32`). SO THE WIDTH IS CONSISTENT --
  unless the adapter does not reach the copyout. For the pid-2 frames regs[8] = 3 (the prototype
  number = 3 for a mmap), which is NOT a prot; on the MIG demux leg the prot comes from the request.
  NOT DECIDED HERE; recorded so the next reader does not "fix" a width that already agrees.

E10. THE CONTRACT OF THE ADAPTER HAS A CONCRETE LISTING VIOLATION *IF* THE LIVE pc IS THE CARD's
====================================================================================================
  IF the device's pc 0x3819d474 executes the card's 0x37C26474 (`ldrb r1,[r1,#0x10]`) -- i.e. S2 in
  records/1034-offset-rule-by-volume.md 5(iii) -- then that byte is the walk AFTER the writer call,
  and the caller's frame pointer (r7) is live to 0x37C264D2. The fault pc is in libobjc, NOT in
  libsystem's -15 stub, and the fault is a LOAD of a NULL object's field, which is the call-walk's
  ONE instruction. That reading needs NOTHING from the trap-15 adapter: launchctl[2] would abort
  simply because the shared-cache objc class list it walks has an entry whose ISa-less block is
  NULL -- e.g. because the class preoptimization list was never built (getPreoptimizedClass
  returned count = -1 = not preoptimized) and the walk is reading uninitialised block memory.
  IF, instead, S1 holds (pc is the same instruction one slot earlier), the fault is 0x37C26472's
  `adds r0,#1`?? (not a load) -- so S1 cannot explain dfsr 7 at far 0x10. => S2 is the only reading
  of the live pair (pc, far, dfsr) that is internally consistent. THIS IS THE RUNG'S PRIMARY HYPOTHESIS
  and it is testable without any shim decode: a row printing the halfwords at pc and pc-2, plus r1.

E13. THREE "PROBLEMS" THAT ARE NOT, AND ONE THAT IS
====================================================================================================
  (a) THE 2 KiB ALLOCATOR GRANULARITY (E8) does not implicate the wire: every captured pid-2
      vm_map64/vm_allocate64 row RESULTED 0 with a mapped address (1033 supplement 1, N4165-N4176).
      The adapter's job -- read the caller's struct, map, write the address back -- was done 6/6 on
      those calls. The 2 KiB alignment of 0x68000 is therefore a property of the caller's desired
      address/alignment, not a kernel rounding defect. E8's "not resolved" is closed here for the
      wire question.
  (b) "r0 = 0x807 is not a plausible port name" -- it is pid 2's SVC trap word in the trap15 frames,
      not the task port name: the adapter prints it as `r0=` of the FRAME, and on those calls
      port_name_to_task(0x807) succeeded (task == current_task() passed, else nothing would have
      been mapped). 0x807 is a valid name in launchctl's space on this boot. No defect.
  (c) "the adapter refused every call with address64 >> 32" (E6's alarm): REFUTED by (a)'s six
      result=0 rows -- a refusal would be result=4 and no address. E6's rung is therefore NOT the
      primary 1035; the carrier question (E12) is.
  (d) THE ONE THAT IS REAL: the adapter PRINTS the wrong slots for its own mask/size -- its `done:`
      printf prints regs[3] as size_high, regs[2] as size_low, regs[5] as mask_high, regs[4] as
      mask_low, yet calls mach_vm_map with regs[2] as size and regs[4] as mask (code, line 280). The
      printed row and the executed call disagree for any call where regs[3] or regs[5] is not zero;
      on every captured accepted call those are 0, so the rows happened to agree. A 1035 wire row
      must print the EXECUTED arguments (size = regs[2], mask = regs[4]) separately from the raw
      frame, or it repeats this row's defect (a row that cannot say its own conjuncts).
