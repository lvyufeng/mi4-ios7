1034 CALLER DECODE - how iOS 7 userland reaches mach trap -15 (mach_vm_map)
READ-ONLY static analysis. No edit, no build, no device action.
Source: /tmp/dyld-extract/dyld_shared_cache_armv7 (315952666 B).
VA convention: all VAs are DEVICE map0 VAs (no dyld slide).
Card offset = 0x455D000 + (VA - 0x2c000000).

1. TRAP STUBS (libsystem_kernel.dylib __TEXT, VA 0x381c5000 size 0x19000)
======================================================================
Found by scanning 0x381c5000..0x381d9000 for `mov ip,#N; svc #0x80` patterns
(exactly one hit per N; scan window capped at +0x14000, see 6).

WORD OF CAUTION ON BYTE-SCANNING: this image embeds Thumb GOT-binding opcode
blocks (e.g. at VA 0x381d70c0 / 0x381d8b00 the ARM reading is `feedface ...`
but the bytes are Thumb `svc #0x80` + `ldr ip,[pc]` sequences) and run-time
relocated pointer slots that look like `e58f000? ...`. A naive scan of
0x381c5000..0x381d9000 for `mov ip,#N` reports ONE hit per trap N, but that hit
is not necessarily a stub. Only the entries below marked BYTES were verified by
reading the 32-byte unit around them in ARM mode.

register frame either way).

======================================================================
3. r0 = 0x807
======================================================================
The C wrappers never load a literal into r0 before the trap: r0 is argument 1
(task). So 0x807 is mach_task_self's value, set by the caller/userland
(`_mach_task_self_` is an import in image stub clumps, e.g. fo:0xe798476). Bridge from bytes:
  r2-kmsg path stores the pair {self_lo=self, self_hi=0} at [sp+36] (0x381ce28a
  `ldr r1,[r5]; ldr r5,[r5,#4]; str r5,[sp,#40]; str r1,[sp,#36]`), i.e. the
  library treats its task port as an opaque 64-bit-stored 32-bit name supplied
  by _mach_task_self_. Nothing in the cache hard-codes 0x807.
Unproven directly: task_self_trap's return value. The only 0x807-class literal
found is the encoded exports-trie tail `80 55 20 29 40` inside
  "_task_self_trap" at fo:0xe9d40eb / fo:0xebb29bc
  (VA 0x3a959e0f / 0x3c1b29cf); not decoded here (x86_64-format 64-bit
  packed node, 0x2c.../0x382... image-offset split unverified).

5. malloc (Task 3)
======================================================================
libsystem_malloc.dylib is the SMALL variant, VA 0x381fe000 (text to 0x38210000),
_dyld_shared_cache_armv7 only. There is no libsystem_malloc.1 (magazine/scalable
malloc) in this cache.
  -0x381fe90c..0x381fe97e (fo:0xfd390c) = malloc_zone_malloc style wrapper:
      blx zone->malloc (r2 = [r5+12]), then optional malloc_logger hook
      (blx r4 with type 10). No kernel call.
  -Statistical scan: no BL/BLX from 0x381fe000..0x38210000 lands in libsystem_kernel
    __TEXT 0x381c5000..0x381de000 (0 hits).
  -Strings: "*** FATAL ERROR - magazine mask exceeds allocated magazines."
    (fo:0xfdf7ff), "pointer being freed was not allocated" (fo:0xfdf9f1),
    "madvise_free_range" (fo:0xfe1f5a) — generic allocator error text only; no
    mach_vm_map path in code.
    ("magazine" text alone is not evidence of the scalable allocator; the small
     malloc also ships it.)
CONCLUSION: malloc does not reach mach_vm_map in this cache. A malloc shadow that
shows trap -15 frames means either a different image (outside the shared cache)
or a faulting stack, not this allocator's kernel call.

======================================================================
6. The 2 KB oddity (Task 3 continued) - OPEN
======================================================================
Observed r2 values (0x1000, 0x2000, 0xd000, 0x100000, 0x800000) are NOT 2 KB
multiples, and 0x1000 is the iOS page size. The stub passes r2 through untouched.
No rounding constant for 0x800 was found in the path. A r2 = 0x800-class hint
would have to come from the caller; nothing in libsystem_kernel/malloc does it.
Caveat on the -31/-10 hunt: the stub scan was capped at TEXT+0x14000 because from
~0x381d70c0..0x381d8b00 the image contains embedded Thumb GOT-binding opcode
blocks (e.g. fo:0x1d60c2d: 2d 00 00 e0 70 00 00 90 00 00 71 0c 11 40 ...,
and `... e0 15 14 40` at fo:0x1d60e13) whose 0x90/0x71 bytes make any window
look like "data 0x01d....". Earlier patterns at 0x381d7470 / 0x381d7088
/ 0x381d859c / 0x381d8b50 are artifacts of this; do not cite them.
